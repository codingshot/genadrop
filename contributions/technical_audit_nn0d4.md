| 1 | **Exposure of Pinata & Alchemy API keys in the frontend** | The README instructs developers to place Pinata and Alchemy keys in a `.env` file that is read by the React build (`process.env.REACT_APP_*`). When the app is bundled, these values become part of the public JavaScript bundle, allowing anyone who inspects the page to extract the keys and abuse the associated services (unlimited IPFS pinning, node‑request quotas, possible billing fraud). | • Move all secret‑valued calls to a **backend‑only** layer (e.g., Netlify Functions, Vercel Serverless, Firebase Cloud Functions, or a simple Express API). <br>• The frontend only sends a signed request (or JWT) to that backend, which then forwards the request to Pinata/Alchemy using the server‑side keys. <br>**Example (Node/Express)**:<br>```js\n// server/pinata.js\nconst axios = require('axios');\nexpress.post('/api/pinata/pinJSON', async (req, res) => {\n  const { pinataMetadata, pinataContent } = req.body;\n  const pinataApiKey = process.env.PINATA_API_KEY;   // never sent to client\n  const pinataSecretApiKey = process.env.PINATA_SECRET_API_KEY;\n  const pinataEndpoint = 'https://api.pinata.cloud/pinning/pinJSONToIPFS';\n  try {\n    const response = await axios.post(pinataEndpoint, {\n      pinataContent,\n      pinataMetadata\n    }, {\n      headers: {\n        pinata_api_key: pinataApiKey,\n        pinata_secret_api_key: pinataSecretApiKey\n      }\n    });\n    res.json(response.data);\n  } catch (err) {\n    res.status(500).json({ error: err.message });\n  }\n});\n```<br>**Frontend call**:<br>```js\nawait fetch('/api/pinata/pinJSON', {\n  method: 'POST',\n  headers: { 'Content-Type': 'application/json' },\n  body: JSON.stringify({ pinataMetadata, pinataContent })\n});\n``` |
| 2 | **Unrestricted file‑type upload to IPFS via Pinata** | The UI lets users drag‑and‑drop any image (or arbitrary file) to be included in the generative layers. If malicious files (e.g., HTML with JS, executables, or large binaries) are pinned, they become permanently available on IPFS and can be served through any IPFS gateway, opening a vector for phishing, malware distribution, or DoS via large payloads. | • Implement **client‑side MIME‑type validation** (allow only image/* types such as PNG, JPEG, SVG, WebP). <br>• Enforce **size limits** (e.g., ≤ 5 MB per file). <br>• Add a **server‑side sanity check** before calling Pinata: verify the file’s magic bytes and reject non‑image data. <br>**Example (client)**:<br>```js\nconst ACCEPTED_TYPES = ['image/png','image/jpeg','image/svg+xml','image/webp'];\nconst MAX_SIZE = 5 * 1024 * 1024; // 5 MB\nfunction validateFile(file) {\n  if (!ACCEPTED_TYPES.includes(file.type)) throw new Error('Invalid file type');\n  if (file.size > MAX_SIZE) throw new Error('File too large');\n}\n```<br>**Example (server‑side Node)**:<br>```js\nconst fileType = require('file-type');\nexpress.post('/api/pinata/pinFile', upload.single('file'), async (req, res) => {\n  if (!req.file) return res.status(400).send('No file');\n  const type = await fileType.fromBuffer(req.file.buffer);\n  if (!type || !type.mime.startsWith('image/')) {\n    return res.status(400).send('Only image files allowed');\n  }\n  // … forward to Pinata\n});\n``` |
| 3 | **Potential leakage of private keys via EtherJS usage** | The README mentions EtherJS but does not show how wallets are connected. If developers mistakenly store a private key or mnemonic in state (e.g., Redux, Context) or expose it through `window.ethereum` callbacks, an attacker could steal funds via XSS or malicious browser extensions. | • **Never** store private keys or seed phrases in React state, localStorage, or cookies. <br>• Use **WalletConnect** or **MetaMask** provider solely for signing transactions; let the wallet manage the key. <br>• If a custom signer is required (e.g., for gas‑less meta‑transactions), keep the signer in a **secure backend** or a hardware‑security module (HSM). <br>**Documentation snippet**:<br>```md\n## Wallet Connection\n- Use `new ethers.providers.Web3Provider(window.ethereum)` only to obtain a signer.\n- Do **not** export `signer.getAddress()` or `signer.provider` to global scope.\n- Private keys must never appear in the client bundle; keep them server‑side or in a hardware wallet.\n``` |
| 4 | **Insecure Firebase configuration (if used for auth/storage)** | The README lists Firebase as a dependency but does not show rules. Default Firebase Realtime Database / Firestore rules (`allow read, write: if true;`) would let any unauthenticated user read/write user‑generated metadata, NFT listings, or even overwrite IPFS pins via the backend. | • Enable **Firebase Authentication** (email/password, Google, or WalletConnect‑based custom auth). <br>• Set **strict security rules**: <br>```js\n// firestore.rules\nrules_version = '2';\nservice cloud.firestore {\n  match /databases/{database}/documents {\n    match /users/{uid} {\n      allow read, write: if request.auth != null && request.auth.uid == uid;\n    }\n    match /nfts/{nftId} {\n      allow read: if true; // public metadata\n      allow create, update, delete: if request.auth != null && request.auth.uid == resource.data.owner;\n    }\n  }\n}\n```\n• Additionally, enable **App Check** to prevent abuse from unauthorized clients. |
| 5 | **Missing Content Security Policy (CSP) / XSS mitigations** | A generative NFT builder lets users upload custom images and edit metadata via a rich text editor. If the app directly injects user‑provided strings into the DOM (e.g., `dangerouslySetInnerHTML` or `innerHTML`) without sanitization, an attacker could store a malicious SVG with embedded script that executes when the NFT preview is rendered, leading to session theft or wallet draining. | • Implement a **strict CSP** header (e.g., `default-src 'self'; img-src 'self' data: ipfs.io; script-src 'self'; style-src 'self' 'unsafe-inline';`). <br>• Sanitize any user‑generated HTML/ SVG with a library like **DOMPurify** before rendering. <br>**Example (React + DOMPurify)**:<br>```js\nimport DOMPurify from 'dompurify';\nfunction SafeMetadata({ html }) {\n  const cleanHtml = DOMPurify.sanitize(html);\n  return <div dangerouslySetInnerHTML={{ __html: cleanHtml }} />;\n}\n```\n• Also, set `X-Content-Type-Options: nosniff` and `X-Frame-Options: DENY` headers. |
| 6 | **Unverified IPFS gateway usage leading to gateway‑phishing** | The app likely uses a public IPFS gateway (e.g., `ipfs.io/ipfs/<cid>`) to display generated NFTs. If an attacker can control the CID (by uploading a malicious JSON metadata file), they could serve a fake gateway page that mimics the Genadrop UI and tricks users into approving malicious transactions. | • Pin **only** the metadata JSON and assets via Pinata (or a trusted private IPFS cluster). <br>• Serve the content through a **dedicated, whitelisted gateway** that you control (e.g., Cloudflare IPFS gateway with custom domain, or NFT.Storage’s dedicated gateway). <br>• In the UI, always construct the URL using a **constant base** you trust: <br>```js\nconst GATEWAY = 'https://ipfs.genadrop.io/ipfs/';\nconst assetUrl = `${GATEWAY}${cid}`;\n```\n• Optionally, verify the CID’s content hash after fetch (compare with expected hash) before rendering. |

---

### Summary of Recommendations

1. **Never expose service API keys in the client** – move Pinata/Alchemy calls to a secure backend.  
2. **Validate and restrict file uploads** (type, size, magic bytes) both client‑ and server‑side.  
3. **Keep private keys/secrets out of frontend state**; rely solely on wallet providers for signing.  
4. **Secure Firebase (or any BaaS) with proper auth rules and App Check**.  
5. **Defend against XSS** with CSP, DOMPurify, and safe rendering patterns.  
6. **Control IPFS gateway usage** – use a trusted gateway or verify fetched content before display.  

Implementing these changes will close the most obvious logic‑level attack surfaces in the current Genadrop architecture and bring the project in line with standard security practices for NFT‑creation platforms.
